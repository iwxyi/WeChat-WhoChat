# WhoChat PRD

## 1. 背景

WhoChat 是一个面向个人使用的本地聊天辅助应用。它通过截图、OCR、聊天窗口识别和 AI 分析，理解用户当前正在进行的聊天上下文，并根据联系人画像、用户偏好和分组目标生成合适的回复建议。

项目初期重点支持微信 PC 端，但产品架构应保留通用聊天平台能力，后续可扩展到 QQ、Telegram、WhatsApp、Discord、飞书、钉钉等聊天软件。

本项目不以商业化产品为目标，可能开源。设计上应优先采用低侵入、低风险、可解释、用户可控的方式，避免注入客户端、读取私有数据库、批量遍历聊天记录或默认自动发送消息。

## 2. 产品目标

### 2.1 核心目标

- 识别当前聊天软件窗口和当前会话对象。
- 通过截图和 OCR 获取当前可见聊天上下文。
- 支持不同聊天平台、不同窗口尺寸、不同屏幕 DPI、多显示器位置和用户调整过的聊天列表分割线。
- 根据聊天对象画像、聊天记忆、分组目标和用户偏好生成回复建议。
- 提供跟随聊天窗口的小悬浮部件，单行展示 `应用·昵称（分组） 回复1 回复2 回复3`，用户点击即可复制建议回复。
- 提供主页面用于设置、分组策略管理、聊天对象画像查看与整理。
- 默认所有高敏感数据本地保存，尽量减少外发数据。
- 未识别或未选择聊天对象时，AI 回复生成必须阻断；即使用户配置了第三方 Provider 和 API Key，也不得向云端发送未知会话上下文。

### 2.2 用户价值

- 在老板、客户、朋友、暧昧对象等不同关系中快速获得合适的回复思路。
- 避免因为情绪、措辞、上下文遗漏导致回复不合适。
- 帮助用户沉淀每个联系人的偏好、禁忌、历史事项和关系状态。
- 降低重复性社交和商务沟通的心理负担。
- 保持用户对重要关系的主动性，不替用户默认处理需要真诚投入的关系。

### 2.3 非目标

- 不做微信外挂、客户端注入、Hook、破解或读取微信本地数据库。
- 不默认自动发送消息。
- 不后台静默遍历所有联系人和群聊。
- 不自动打开图片、语音、链接、小程序或服务号文章进行批量采集。
- 不承诺完整、准确还原所有历史聊天记录。
- 不把昵称作为唯一稳定身份。

### 2.4 成功指标

首版不以“完整读取聊天记录”为成功标准，而以当前会话辅助是否稳定可用为标准。

MVP 成功指标：

- 用户打开微信聊天页后，悬浮窗能在 2 秒内跟随显示。
- 当前页面为微信单聊时，页面类型识别准确率达到可用水平。
- 当前可见文本消息 OCR 后，主要语义可被回复生成使用。
- 点击回复建议后，剪贴板内容与展示文本一致。
- 非聊天页、设置页、搜索页、文章页默认不触发 AI 请求。
- 滚动、移动窗口、切换会话时不会产生连续无意义 OCR 或 AI 请求。
- PaddleOCR 最近耗时偏慢时，自动采集会主动降频或跳过，并在诊断中展示性能分级和退避原因。
- 聊天对象不确定时，不写入长期画像。

非 MVP 成功指标：

- 完整识别全部历史聊天。
- 自动识别所有微信页面。
- 自动采集所有聊天对象画像。
- 自动发送消息。

## 3. 产品形态

### 3.0 UI/UX 设计原则

- 主导航使用用户能理解的业务词汇，例如“聊天对象”，避免把群聊隐藏在“好友”概念下。
- 页面信息密度高但分层清晰：先显示当前状态和可执行动作，再显示详细证据和调试信息。
- 同一个数据对象只使用一个主名称，平台、会话类型、Person 身份作为辅助标签，避免重复和歧义。
- 每个阻断状态必须说明“为什么不能继续”和“用户可以做什么”，不能只显示 `blocked` 或 `unknown`。
- 用户手动点击“运行采集管线”但未启动时，必须显示具体阻断原因，并刷新运行态和窗口诊断摘要，不能只给泛化失败提示。
- 总览页和悬浮窗都应同时显示状态与下一步建议，减少用户来回翻日志；当前页面或安全链路阻断时，悬浮窗必须置灰旧建议。
- 总览页应提供单行主动作摘要，从窗口、页面、联系人、采集、OCR、隐私和 AI 链路中提取当前最需要用户处理的一项；详细表格只作为证据层。
- 诊断页必须直接展示联系人识别/入库状态，区分标题缺失、标题候选被过滤、OCR warning、非聊天页阻断和已创建疑似联系人，不能只把这些信息藏在日志里。
- 诊断页必须直接展示目标窗口候选的前景状态、匹配状态、匹配或排除原因，并给出下一步动作，例如切回聊天主窗口、关闭图片预览、补充匹配规则或重新校准。
- 用户应能单独刷新和复制目标窗口诊断摘要；复制内容必须脱敏，避免窗口标题中的手机号、密钥、链接等敏感信息泄漏。
- 悬浮窗的位置贴靠状态不得覆盖 OCR、AI、隐私阻断等业务状态；贴靠边缘可以作为 tooltip 或诊断字段保留。
- 高风险操作如合并身份、清空记录、允许云端 AI 必须显示影响范围、保留内容和不可逆性。
- 列表支持搜索、筛选和排序；详情页保持上下文，不因编辑操作让用户丢失当前选择。
- 联系人确认、分组变更、云端授权和手动回复保护等关键操作完成后，列表、详情页、总览状态链和悬浮窗必须同步刷新。
- 群聊成员、跨平台身份和低置信度候选必须使用“待确认/候选”表达，不能展示成已经确定的事实。
- 设置页保存前必须做一致性校验，拦截无效云端接口地址、空模型名称、空 OCR 语言、无目标应用等会导致主路径不可用的配置。
- 颜色、间距、字体和控件尺寸适配不同 DPI、主题和窗口尺寸；不能依赖固定像素才能正常阅读。
- 空状态必须给出下一步行动，例如“打开一个私聊或群聊”“重新校准区域”，不能只显示“暂无数据”。

### 3.1 主窗口

主窗口用于配置和数据管理，包含：

- 基础设置
- 模型配置
- 自定义 AI Provider 配置
- OCR 配置
- 平台适配器配置
- 分组策略管理
- 聊天对象画像管理
- 聊天记忆查看与整理
- 风险控制设置
- 数据导入、导出、清理
- 调试与诊断模块

主窗口应保持几个长期可用的调试和查看模块，帮助用户确认系统是否识别正确：

- 控制台日志
  - 日志应简洁、精准、可过滤。
  - 默认显示关键事件，例如窗口识别、区域识别、页面分类、联系人切换、OCR 开始/结束、AI 请求开始/结束、错误和暂停原因。
  - 支持按级别过滤：debug、info、warning、error。
  - 支持复制当前日志。

- 环境自检
  - 展示 Python 版本、操作系统、核心依赖、可选 OCR 依赖、数据目录写入能力和密钥后端状态。
  - 自检不得初始化 PaddleOCR 等重型模型，只检查依赖可用性。
  - 复制诊断日志和保存调试样本时应包含环境自检结果。
  - 复制诊断日志和保存调试样本必须在导出边界执行最终脱敏，避免日志误写入 API Key、Bearer Token、手机号、邮箱、URL 或长数字后被外发。

- 反馈质量摘要
  - 诊断页应展示最近回复反馈数量、好用/不合适计数和候选短预览。
  - 复制诊断包和保存调试样本时应包含反馈摘要与结构化反馈记录，并执行最终脱敏。

- 当前状态面板
  - 当前目标应用。
  - 当前窗口位置。
  - 当前页面类型和置信度。
- 当前聊天对象。
  - 当前分组。
  - 当前主题：light、dark、unknown。
  - OCR 状态。
  - AI 请求状态。
  - 暂停原因。

- 目标应用设置
  - 默认启用微信，其他平台预设默认关闭。
  - 用户可以多选启用目标聊天应用。
  - 用户可以新增自定义目标应用，预设应用只能禁用，自定义应用可以删除。
  - 用户可以编辑每个目标的进程名、窗口标题关键词和排除标题关键词匹配规则。
  - 只有当前前台窗口属于已启用目标时才跟随和采集；后台、最小化或被其他前台窗口覆盖的目标只进入诊断候选，不触发截图、OCR 或 AI。
  - 多个白名单聊天应用可以同时启用，例如微信、QQ、Telegram；当前前台命中哪个目标，就按哪个平台解析为 `APP + 昵称` 联系人线索。
  - 目标应用可以声明非聊天子窗口排除项，例如微信的图片视频预览、设置、转发和选择联系人窗口；这些窗口即使进程名匹配，也不得触发截图、PaddleOCR 或回复生成。

- 当前聊天记录面板
  - 展示当前可见消息。
  - 展示消息归属：我、对方、群成员、系统、未知。
  - 展示 OCR 置信度和是否部分截断。
  - 展示消息时间、观察时间和时间来源。
  - 支持标记 OCR 错误。

- 当前聊天对象画像面板
  - 展示当前私聊或群聊的画像、备注、别名、分组和记忆。
  - 支持编辑画像。
  - 支持合并聊天对象或链接真实人身份。
  - 支持将 AI 提取的新记忆确认或丢弃。

- 聊天对象和分组列表
  - 左侧展示已识别私聊和群聊。
  - 支持按平台、分组、最近活跃、是否确认、是否有低置信度数据筛选。
  - 点击聊天对象后进入详情页。

- 聊天对象详情页
  - 展示聊天对象画像。
  - 展示聊天记录和会话摘要。
  - 展示所有别名和合并历史。
  - 展示分组策略和该聊天对象的特殊回复偏好。
  - 展示该聊天对象最近的回复反馈，包括“好用/不合适”计数、候选标签、风险、页面类型、上下文 hash 和短预览。
  - 支持删除、导出或清空该聊天对象的数据。

### 3.2 悬浮小部件

悬浮小部件跟随聊天软件窗口显示，初期重点跟随微信窗口。

核心能力：

- 自动跟随微信窗口移动、缩放、隐藏和显示。
- 显示当前识别到的联系人或会话名称。
- 显示当前分组策略和 AI 回复状态。
- 显示当前页面状态，例如聊天页、服务号页、新闻页、未知页。
- 显示 1 到 3 条 AI 回复建议，用户可在设置中调整可见数量。
- 点击建议后复制到剪贴板。
- 当页面、联系人、隐私或 AI 状态阻断时，不展示可复制的固定假建议。
- 可选支持“填入输入框但不发送”。
- 提供暂停、刷新、隐藏入口。
- 支持设置贴靠优先位置、透明度和回复建议数量。

默认交互：

1. 用户打开微信聊天窗口。
2. 悬浮窗识别当前会话。
3. 应用截图并 OCR 当前可见聊天记录。
4. AI 生成候选回复。
5. 用户点击某条建议，文本复制到剪贴板。
6. 用户手动粘贴并发送。

悬浮窗状态：

- active：当前页面可用，展示回复建议。
- reading：正在稳定截图或 OCR。
- waiting：等待用户打开聊天页。
- paused：用户主动暂停。
- blocked：页面类型、联系人或区域识别置信度不足。
- error：OCR、模型或窗口跟踪出现错误。

悬浮窗约束：

- 不应遮挡微信输入框和发送按钮。
- 不应抢占用户输入焦点，除非用户点击悬浮窗。
- 支持拖动改变贴靠位置。
- 支持透明度设置。
- 支持底部、顶部、右侧、左侧和自动贴靠优先级。
- 支持一键隐藏和一键暂停。

## 4. 用户场景

### 4.1 奉承老板

用户希望回复老板时显得积极、靠谱、尊重对方时间。

系统应：

- 支持用户创建领导类分组。
- 支持用户为同一类关系设置不同目标，例如应付、迎合、推进工作、保持边界、表达不满等。
- 根据用户为该分组设置的目标生成回复，而不是写死“奉承”或“积极”。
- 避免违背用户明确设置的语气、边界和禁忌。

### 4.2 应付客户

用户希望回复客户时专业、明确、推动进展。

系统应：

- 识别客户分组。
- 根据历史事项、项目状态和客户偏好生成回复。
- 避免过度承诺、模糊表述和引发误会的措辞。

### 4.3 搭讪或暧昧聊天

用户希望自然推进关系，避免生硬、油腻或越界。

系统应：

- 根据对方语气和历史互动判断热度。
- 生成自然、轻松、有互动点的回复。
- 在对方冷淡、拒绝或表达不适时提示降低推进强度。

### 4.4 朋友日常应对

用户希望保持关系但减少沟通消耗。

系统应：

- 生成自然、短、像真人的回复。
- 避免过度正式和明显 AI 风格。
- 根据对方近期状态适度加入关心或回应。

## 5. 功能需求

### 5.1 平台适配

系统应采用平台适配器架构。

```text
App Core
├─ Window Tracking
├─ Screenshot Capture
├─ OCR Engine
├─ Layout Parser
├─ Conversation State
├─ Contact/Profile Memory
├─ Strategy Engine
├─ Reply Generator
└─ Platform Adapters
   ├─ WeChat Adapter
   └─ Generic Chat Adapter
```

适配器职责：

- 检测目标应用是否运行。
- 获取目标应用窗口位置和尺寸。
- 判断当前页面类型。
- 定位聊天列表区域。
- 定位聊天记录区域。
- 定位顶部标题区域。
- 解析当前可见消息。
- 区分自己、对方、群成员和未知发言人。

适配器输出必须带置信度。核心逻辑不得把适配器输出视为绝对事实。

### 5.2 微信适配

微信 PC 端为第一优先级。

微信适配器应支持：

- 根据窗口标题、进程、控件或截图特征识别微信窗口。
- 识别顶部昵称或群聊标题。
- 识别左侧聊天列表区域。
- 识别右侧聊天记录区域。
- 判断页面类型：
  - 单人聊天
  - 群聊
  - 公众号或服务号
  - 新闻或订阅内容
  - 系统页面
  - 文件传输助手
  - 未知页面
- 根据气泡位置、头像位置、文本框坐标和颜色辅助判断消息归属。
- 支持微信日间和夜间主题。

颜色识别原则：

- 不依赖固定 RGB。
- 优先使用几何布局、OCR 坐标、头像位置和气泡轮廓。
- 颜色只作为辅助特征。
- 根据背景平均亮度判断 light、dark 或 unknown 主题。

### 5.3 微信窗口区域识别

微信窗口内通常包含左侧导航栏、聊天列表、右侧内容区和顶部标题区，但不同版本、窗口尺寸、DPI 缩放、登录状态、页面类型和主题都会导致布局差异。因此区域识别不能只依赖固定坐标。

区域识别应采用多信号融合：

1. 默认布局先验
   - 微信 PC 端左侧通常为窄导航栏。
   - 导航栏右侧通常为聊天列表。
   - 窗口右侧大面积区域通常为当前会话或内容页。
   - 顶部区域通常包含当前会话标题、搜索、更多操作等。

2. 视觉分割线检测
   - 在窗口截图中检测纵向边界线和背景色块变化。
   - 优先寻找左侧导航栏与聊天列表之间的边界。
   - 再寻找聊天列表与右侧内容区之间的主分割线。
   - 日夜间主题下使用相对亮度差和边缘密度，不使用固定颜色。

3. OCR 辅助
   - 左侧聊天列表通常包含多行联系人名、摘要和时间。
   - 右侧聊天记录区通常包含气泡文本、居中时间戳、图片、语音、表情。
   - 顶部标题通常为较短文本，位置接近右侧内容区上方居中或偏左。
   - 服务号、新闻、设置页面会出现不同结构的标题、正文和按钮文本。

4. 控件和图标辅助
   - 聊天列表中通常存在搜索框、会话条目、头像、未读红点。
   - 聊天页底部通常存在输入框、表情按钮、文件或截图按钮。
   - 非聊天页可能缺少输入框，或出现文章正文、菜单、网页式内容。

5. 用户校准
   - 首次运行时允许用户手动框选聊天列表区域和聊天记录区域。
   - 校准结果按微信版本、窗口尺寸比例、DPI、主题保存。
   - 自动识别低置信度时，应提示用户重新校准。
   - 当微信窗口分割线被用户拖动后，系统应能检测布局漂移，并允许重新校准。

区域识别策略：

- 必须同时支持自动识别和用户手动校准。
- 自动识别用于降低首次使用成本和适配窗口变化。
- 用户校准用于处理微信布局调整、DPI 缩放、特殊窗口尺寸和自动识别失败。
- 自动识别和用户校准结果发生冲突时，优先使用用户校准。
- 用户校准可以通过截图覆盖层完成：在微信窗口截图上拖拽框选聊天列表区、聊天记录区、标题区和输入区。
- 覆盖层应只用于配置，不应常驻遮挡微信。
- 校准结果应保存为相对窗口比例，而不是绝对屏幕坐标。
- 当窗口尺寸变化后，按比例恢复区域；如果恢复后的区域置信度下降，则提示重新校准。

布局漂移检测：

- 定期检查聊天列表与内容区分割线是否偏离已校准位置。
- 如果右侧消息气泡明显出现在校准聊天列表区域，或左侧联系人条目明显出现在内容区，应判定为区域漂移。
- 如果底部输入框不在预期区域，应降低当前页面置信度。
- 漂移轻微时自动调整；漂移较大时暂停识别并提示重新校准。

区域结构建议：

```json
{
  "window_rect": [0, 0, 1200, 800],
  "nav_rect": [0, 0, 60, 800],
  "chat_list_rect": [60, 0, 260, 800],
  "content_rect": [320, 0, 880, 800],
  "title_rect": [320, 0, 880, 64],
  "message_rect": [320, 64, 880, 600],
  "input_rect": [320, 664, 880, 136],
  "confidence": 0.87,
  "source": "auto | calibrated | mixed"
}
```

页面类型分类：

```text
chat_dm          单人聊天
chat_group       群聊
file_helper      文件传输助手
official_account 公众号或服务号
news_article     新闻或文章页
mini_program     小程序页
search           搜索页
settings         设置页
media_viewer     图片或视频查看器
unknown          未知页面
```

页面分类信号：

- 是否存在底部输入框。
- 是否存在右侧聊天气泡结构。
- 是否存在居中时间戳。
- 是否存在群成员昵称行。
- 是否出现文章标题、正文段落、公众号菜单或网页式滚动内容。
- 是否出现图片查看器的黑色背景或浮层工具栏。
- 是否出现搜索框和搜索结果列表。
- 当前顶部标题是否能与左侧选中会话对应。

处理规则：

- 只有 `chat_dm`、`chat_group`、`file_helper` 可进入回复建议流程。
- `official_account`、`news_article`、`mini_program`、`settings`、`media_viewer`、`search` 默认不生成聊天回复。
- 已被目标应用排除标题命中的子窗口应在窗口跟踪阶段阻断，不进入截图和 OCR 阶段。
- 页面类型为 `unknown` 时只允许用户手动刷新或重新校准，不写入长期记忆。
- 页面分类置信度低时，悬浮窗应显示暂停状态。
- 设置页、公众号或服务号、新闻或文章页的 OCR 特征应优先于聊天页启发式，避免其正文或菜单被误当作聊天消息。
- 当左侧区域被设置页、搜索页、弹层或其他内容覆盖时，应临时禁用依赖左侧聊天列表的联系人识别。
- 如果右侧仍能明确识别为当前聊天页，可继续使用顶部标题和历史会话状态生成低风险建议。
- 如果左侧和右侧都无法确认页面类型，应暂停 OCR 入库和 AI 请求。
- 禁止为了“可能没损失”而继续写入长期记忆；误判的主要损失是污染联系人画像和触发无意义 AI 请求。

### 5.4 截图覆盖层与用户校准

系统应提供类似截图标注的覆盖层，用于用户手动指定或修正关键区域。

覆盖层能力：

- 显示当前微信窗口截图。
- 支持拖拽框选区域。
- 支持调整区域边界。
- 支持预设区域类型：
  - 左侧导航栏
  - 聊天列表
  - 顶部标题
  - 聊天记录
  - 输入框
- 支持实时预览 OCR 检测结果。
- 支持保存、重置、重新自动识别。
- 支持按主题、DPI、窗口比例保存多套布局。

校准触发条件：

- 首次启动微信适配器。
- 自动区域识别置信度低。
- 页面结构与历史校准明显不匹配。
- 用户拖动微信分割线后导致区域漂移。
- OCR 结果大量落在错误区域。
- 用户在悬浮窗或主窗口中手动点击“重新校准”。

### 5.5 截图与 OCR

系统应通过截图获取聊天区域内容。

要求：

- 支持截取整个微信窗口。
- 支持只截取聊天记录区域。
- 支持只截取顶部标题区域。
- OCR 结果应保留文本、坐标、置信度、截图来源。
- 每次采集应保留结构化元数据，例如截图 hash、OCR 裁剪区域、OCR 引擎、页面分类、消息数量和是否保留截图原图；元数据默认不包含聊天正文。
- OCR 结果不应直接等同于可靠聊天记录，需要经过版面解析和置信度处理。
- 系统应避免在窗口滚动、拖动、缩放过程中持续高频 OCR。
- OCR 请求应经过防抖、节流和内容变化检测。
- 应提供结构化 golden 样本回放，用于持续验证 OCR 页面分类、消息归属和 partial 处理。
- 应提供截图样本回放，用于沉淀脱敏真实微信截图、对应 layout、OCR 框和 expected 断言，支持在不访问真实桌面的环境中复现识别问题。
- 群聊标题、成员昵称行和群聊正文需要分开处理；成员昵称行不能作为正文消息入库。

### 5.6 页面适配与响应式布局

聊天软件窗口不是固定尺寸。用户可能使用笔记本小屏、外接 4K 屏、纵向屏、多显示器、系统缩放、微信深浅色模式，也可能手动拖动左侧聊天列表和右侧聊天内容之间的分割线。

系统必须遵循这些原则：

- 所有版面区域都以窗口相对比例保存，而不是保存固定屏幕坐标。
- 自动估算只能作为初始候选，不能替代用户校准。
- 自动估算要按窗口尺寸和宽高比选择布局 profile，例如 compact、standard、wide。
- 多显示器和负坐标窗口必须正常工作，不能假设窗口左上角从 `(0, 0)` 开始。
- 不同平台适配器必须通过统一的 `PlatformAdapter` 接口输出 `LayoutRegions`。
- 微信专有启发式只能放在 WeChat adapter 中，不能污染通用聊天适配。
- 当窗口尺寸过小、内容区过窄或区域重叠时，应暂停 OCR 入库和 AI 请求。
- OCR 区域归属必须基于当前 layout 动态计算，不能使用固定屏幕坐标。

消息结构建议：

```json
{
  "message_id": "local_uuid",
  "conversation_id": "local_uuid",
  "speaker": "me | other | member | system | unknown",
  "speaker_name": "optional",
  "text": "消息文本",
  "content_type": "text | image | emoji | voice | file | link | mixed | unknown",
  "bbox": [0, 0, 0, 0],
  "ocr_confidence": 0.92,
  "source_screenshot_id": "local_uuid",
  "observed_at": "2026-08-03T11:00:00+08:00",
  "message_time": null,
  "time_precision": "exact | day | range | approximate | unknown",
  "time_source": "ocr | inferred | observed | manual | none",
  "partial": false,
  "fingerprint": "hash"
}
```

### 5.6 滚动、防抖与性能控制

聊天窗口滚动时，截图内容可能快速变化。如果每一帧都触发 OCR 和 AI 请求，会造成性能浪费、上下文抖动和费用浪费。

系统必须实现防抖、节流和去重。

截图触发策略：

- 窗口静止后再截图。
- 滚动停止后延迟一小段时间再 OCR。
- 窗口移动、缩放、切换会话时暂停 OCR，等待稳定。
- 连续截图内容相似度高时不重复 OCR。
- 当前页面类型未确认时不触发 AI 请求。

建议默认参数：

```text
window_stable_delay_ms = 300
scroll_debounce_ms = 900
ocr_min_interval_ms = 30000
ai_min_interval_ms = 3000
max_pending_ocr_jobs = 1
max_pending_ai_jobs = 1
```

当 OCR Provider 为 PaddleOCR 时，自动采集必须使用更保守的最低间隔；连续超时、子进程失败或输出不可解析时，应进入短期熔断，避免反复初始化模型造成系统卡顿或主程序退出。默认重 OCR 间隔不低于 30 秒，PaddleOCR worker 默认 90 秒超时。

自动采集还应参考最近采集样本中的标题 OCR、消息区 OCR 和总耗时：

- 最近 PaddleOCR 平均总耗时不超过 15 秒时，保持默认节流。
- 平均总耗时超过 15 秒时进入 warning，自动采集间隔至少拉长到平均耗时的 2 倍。
- 平均总耗时超过 45 秒时进入 slow，自动采集间隔至少拉长到平均耗时的 3 倍或 60 秒以上。
- 手动触发的采集不受这层自动降频影响，但仍受管线运行中拒绝排队、超时和熔断保护。

内容变化检测：

- 对聊天记录区域生成感知哈希或轻量图像 hash。
- hash 与上次差异低于阈值时跳过 OCR。
- OCR 后消息指纹无变化时跳过 AI 请求。
- 只在最近可见消息、联系人、分组策略或画像发生有效变化时重新生成回复。

滚动状态处理：

- 检测到滚动中时，悬浮窗显示“正在读取”或“滚动中暂停”。
- 滚动期间不写入长期记忆。
- 滚动停止并稳定后再合并上下文。
- 用户手动触发“采集更多上下文”时，可以连续滚动采集，但必须限速、限页数、可取消。

AI 请求控制：

- AI 请求必须基于稳定消息快照。
- 同一联系人、同一上下文 hash、同一策略下不得重复请求。
- 新请求发起时，如果旧请求仍在进行，应取消旧请求或丢弃旧结果。
- AI 结果返回后，如果当前联系人已变化，结果不得展示到悬浮窗。
- 低置信度页面、未知联系人或未知页面类型不发起 AI 请求。

后台任务模型：

- 截图、OCR、消息解析、AI 请求应放入异步任务队列。
- UI 线程不得直接执行耗时 OCR 或网络请求。
- PaddleOCR 等重型本地 OCR 应优先使用常驻隔离 worker 复用模型，避免每次采集都重新初始化模型。
- 每类任务应支持取消和超时。
- 同一会话只保留最新的待处理任务。
- 任务结果必须带 `conversation_id`、`snapshot_hash` 和生成时间，避免旧结果覆盖新状态。
- 应用退出时必须统一停止窗口轮询、自动采集定时器、采集线程池、回复线程池和 OCR worker；PaddleOCR daemon 不得在主程序退出后残留。
- 用户切换 OCR Provider 时必须先释放旧 OCR 引擎和 worker，再启用新引擎，避免后台模型进程残留。

### 5.7 聊天上下文拼接

系统需要将多次截图中的 OCR 结果拼接为相对稳定的消息流。

要求：

- 根据文本、坐标、顺序和截图重叠区域去重。
- 识别上下滚动后重复出现的消息。
- 对被截断的消息标记 `partial = true`。
- 对无法确定顺序或归属的消息标记低置信度。
- 低置信度消息默认不写入长期记忆。
- 不允许 LLM 编造聊天内容来补全 OCR 缺失。

时间处理：

- 每条消息必须记录 `observed_at`。
- OCR 到聊天时间时记录 `message_time`。
- 无法识别真实聊天时间时，`message_time` 为空。
- 支持根据时间锚点为附近消息建立时间范围。
- 允许后续滚动看到更多时间锚点后回填时间信息。
- 如果当前页面疑似旧历史记录，应标记为 `history_snapshot`。

### 5.8 当前会话识别

系统应识别当前正在查看的会话，但不能只依赖昵称。私聊和群聊都属于聊天对象，都可以分配同一套分组策略。

聊天对象实体结构建议：

```json
{
  "contact_id": "local_uuid",
  "platform": "wechat",
  "conversation_type": "dm | group | official | system | unknown",
  "current_display_name": "张三",
  "aliases": ["张三", "三哥"],
  "avatar_fingerprint": "optional",
  "manual_confirmed": false,
  "merged_into": null,
  "created_at": "2026-08-03T11:00:00+08:00",
  "updated_at": "2026-08-03T11:00:00+08:00"
}
```

要求：

- 顶部昵称作为当前会话线索，不作为唯一主键。
- 平台联系人以 `APP + 昵称` 作为识别线索，例如 `微信·小红`、`Telegram·大红`。
- `Contact` 表示某个平台上的聊天对象；`Person` 表示用户手动确认后的真实人。
- 用户可以把多个平台聊天对象链接到同一个 Person，但系统不得只因为昵称相同自动合并。
- 支持用户手动确认联系人。
- 支持用户手动合并联系人。
- 合并联系人时保留别名和历史记忆。
- 支持联系人黑名单。
- 支持群聊和个人聊天分开建模，但二者都可以分配分组策略。

真实人身份结构建议：

```json
{
  "person_id": "local_uuid",
  "display_name": "小红",
  "aliases": ["小红", "大红"],
  "linked_contacts": ["微信·小红", "Telegram·大红"],
  "status": "suspected | confirmed | rejected"
}
```

群成员结构建议：

```json
{
  "group_member_id": "local_uuid",
  "group_contact_id": "wechat_group_contact",
  "member_display_name": "产品同学",
  "person_id": "optional_person",
  "platform_contact_id": "optional_friend_contact",
  "confidence": 0.72,
  "source": "ocr | manual | import"
}
```

联系人确认等级：

```text
unconfirmed   仅根据当前标题或 OCR 推断
suspected     与历史联系人可能匹配
confirmed     用户手动确认
merged         已被合并到其他联系人
ignored        用户选择忽略或拉黑
```

写入规则：

- `unconfirmed` 联系人只允许使用临时上下文生成回复。
- `suspected` 联系人可以提示用户确认或合并。
- 只有 `confirmed` 联系人可写入长期画像。
- `ignored` 联系人不触发 OCR 入库和 AI 请求。

### 5.9 分组策略

用户可以为聊天对象分配分组。私聊和群聊使用同一套分组策略，不分两套系统。不同分组对应不同回复目标、语气和禁忌。

分组策略必须用户可编辑，不得写死。系统可以提供预设模板，但模板只是初始配置，用户可以新增、删除、重命名和调整。

分组策略应支持归档/恢复。归档不删除历史引用，已分配的聊天对象仍保留原策略；新分配默认只展示启用策略。

预设分组建议：

- 领导
- 客户
- 暧昧或搭讪
- 朋友
- 同事
- 默认
- 手动回复保护

分组策略结构建议：

```json
{
  "group_id": "boss",
  "name": "领导",
  "goal": "用户自定义目标",
  "mode": "应付 | 迎合 | 推进工作 | 保持边界 | 表达不满 | 自定义",
  "tone": "用户自定义语气",
  "avoid": ["抱怨", "甩锅", "过度解释"],
  "reply_variants": ["稳妥版", "简短版", "自定义版"],
  "requires_manual_reply": false
}
```

要求：

- 每个分组都必须有明确的用户目标。
- 同一个预设分组可以派生多个用户自定义分组，例如“领导-应付”“领导-迎合”“领导-保持距离”。
- 分组列表支持搜索目标、语气和禁忌，并可显示已归档策略。
- 聊天对象可以覆盖分组策略，设置专属目标、语气和禁忌。
- 回复生成必须以用户配置为准，而不是以系统对关系类型的刻板假设为准。
- 对可能伤害关系或明显带有攻击性的目标，应提示风险，但不替用户做道德判断。
- “家人”“亲戚”等亲密关系不作为默认可自动辅助分组。
- 用户如手动创建亲密关系分组，默认启用 `requires_manual_reply = true`。
- 手动回复保护分组只允许整理画像和展示上下文，不主动生成可复制回复，除非用户临时确认。
- 软件应保留人性边界：对需要真诚表达的关系，默认鼓励用户亲自回复。

### 5.10 聊天对象画像与聊天记忆

聊天对象画像应分层保存。

画像类型：

- 稳定事实：职业、关系、项目、偏好、重要背景。
- 沟通偏好：喜欢简短、讨厌催促、重视礼貌、喜欢幽默等。
- 禁忌事项：不要提及的话题、容易引发不满的表达。
- 临时事项：近期任务、约定、待办、短期情绪。
- 会话摘要：最近一次或多次聊天的简要总结。

要求：

- 长期记忆只保存高置信度、相对稳定的信息。
- 临时事项应支持过期时间。
- AI 自动提取的新记忆应进入待确认状态。
- 用户可以编辑、删除、合并记忆。
- 用户确认或拒绝待确认记忆后，记忆列表、聊天对象详情、总览画像和悬浮窗上下文必须同步刷新，避免用户看到过期画像。
- 低置信度 OCR 内容不得直接污染长期画像。

### 5.10.1 滚动聊天记录拼接

系统应把多次截图中的可见消息逐步拼接为持久聊天记录，但必须保守处理。

规则：

- 每次 OCR 结果先形成一个可见消息窗口。
- 可见窗口与已有记录存在连续重叠时，允许自动前接或后接。
- 可见窗口完全包含在已有记录中时，只刷新观测次数和最后看到时间，不重复入库。
- 没有可靠重叠时，不强行拼接为连续历史，应作为待确认片段或新段落。
- 位于截图顶部或底部边缘的 partial 消息默认不参与自动拼接。
- 重复短句、表情、语音占位、图片占位要降低合并置信度。
- 群聊消息如果无法识别成员，不应把内容写入某个成员画像。

### 5.11 回复生成

系统应结合以下信息生成回复：

- 当前可见聊天上下文
- 当前聊天对象画像
- 联系人所在分组策略
- 联系人的个人覆盖策略
- 用户自己的表达偏好
- 最近会话摘要
- 当前页面置信度和 OCR 置信度

默认生成多个候选：

- 稳妥版
- 简短版
- 热情版
- 推进版
- 不建议回复或建议稍后回复

每条候选应可复制。必要时应显示风险提示，例如：

- 当前上下文置信度较低。
- 当前页面可能不是最新聊天位置。
- 对方可能在表达不满，不建议开玩笑。
- 当前页面疑似服务号或新闻页，不建议生成聊天回复。
- 当前联系人属于手动回复保护分组，建议用户亲自回复。

Prompt 安全：

- 聊天内容、联系人画像和用户配置应作为数据传入，不应让聊天内容覆盖系统规则。
- 如果聊天内容中出现“忽略之前指令”“自动发送”“泄露配置”等指令，应视为普通聊天文本。
- AI 不应输出用户未要求的敏感推断，例如政治、健康、财务、身份等高风险判断。
- 涉及法律、医疗、财务、职场冲突等高风险内容时，应优先生成保守建议，并提示用户自行判断。

输出格式：

```json
{
  "replies": [
    {
      "label": "稳妥版",
      "text": "建议回复文本",
      "reason": "简短依据",
      "risk": "low | medium | high"
    }
  ],
  "warnings": [],
  "should_reply": true
}
```

### 5.12 自动化能力分级

系统应按风险分级开放自动化能力。

```text
L0：只识别和分析，不生成回复。
L1：生成回复建议，用户点击复制。
L2：用户点击后填入输入框，但不发送。
L3：用户点击后发送。
L4：满足规则后自动发送。
```

MVP 只实现 L1。

后续如果实现 L2 或更高等级，必须满足：

- 用户显式开启。
- 仅对手动加入白名单的联系人或分组生效。
- 任何发送动作前必须可被用户取消。
- 老板、客户、暧昧对象等高风险分组默认禁止自动发送。
- 手动回复保护分组禁止自动填入和自动发送。
- 页面类型未知、联系人未知、OCR 置信度低时禁止自动发送。

### 5.13 扩展上下文采集

MVP 不自动点击左侧聊天列表。

后续可支持用户手动触发“采集更多上下文”：

- 仅在当前会话内模拟向上滚动。
- 不点击左侧聊天列表。
- 限制最大滚动页数。
- 每次滚动后确认仍处于同一会话。
- 识别到非聊天页、图片查看器、链接页、服务号页、搜索页时停止。
- 采集完成后提示用户当前采集范围和置信度。

自动点击左侧聊天列表属于高风险能力，不进入 MVP。

## 6. 非功能需求

### 6.1 隐私与数据安全

- 默认本地保存联系人、聊天摘要、画像和配置。
- 支持关闭长期记忆。
- 支持联系人黑名单。
- 支持一键暂停采集。
- 支持清空某个联系人或全部数据。
- 云端模型调用前应尽量裁剪上下文并支持敏感信息脱敏。
- 应明确展示哪些内容会被发送给 AI 模型。
- API Key 不应明文写入日志。
- 支持设置数据保留期限。
- 回复反馈等行为数据应支持独立保留期限，并在本地清理时从 SQLite 删除过期记录。
- 支持只使用本地模型的离线模式。
- 支持禁止保存截图原图。
- 导出数据应提示包含敏感聊天内容。
- 全局导出和联系人导出中的系统日志、生成审计、Provider 状态、设置审计等元数据必须执行最终脱敏；聊天正文和记忆作为用户主动导出的数据可以保留原文，但导出界面必须提醒其敏感性。

### 6.2 权限与系统兼容

- 首版目标系统为 Windows。
- 支持多显示器。
- 支持不同 DPI 缩放。
- 支持窗口最大化、普通窗口和最小化状态。
- 使用 Win32 API 判断最小化和当前前台窗口；最小化或非前台目标窗口默认暂停采集。
- 如果截图或窗口跟踪需要额外权限，应在 UI 中说明原因。
- 程序不应默认请求管理员权限。
- 如果目标应用以管理员权限运行导致无法自动化，应提示用户权限不一致。
- 如果仅通过窗口标题匹配而未读取到进程名，应在诊断中提示用户补充进程名规则或检查权限。
- 当前前台聊天探针应能输出目标窗口、截图路径、标题裁剪路径、标题 OCR 耗时、标题候选数量、可选消息区解析结果，并支持脱敏模式；阻断时应输出相关窗口候选、前景状态和阻断原因，并支持延迟执行以便用户切换到目标窗口。

### 6.3 稳定性

- 微信窗口不存在时不报错。
- 微信最小化时悬浮窗隐藏。
- 微信移动或缩放时悬浮窗平滑跟随。
- OCR 失败时显示明确状态。
- 页面类型未知时不生成或只生成低置信度建议。
- 网络请求失败时保留本地状态并展示可重试。
- AI Provider 连续失败进入退避时，应展示健康状态和可手动恢复入口。
- Provider 退避状态应本地持久化，应用重启后不能立即绕过退避。
- Provider 退避过期后可以本地转入 recovering 状态，但不应未经用户触发就发起云端重试。
- 模型返回格式异常时不得崩溃。
- SQLite 写入失败时应给出错误并停止写入长期记忆。

### 6.4 可解释性

- 回复建议应能展示简短依据。
- 回复建议面板应以紧凑摘要展示本次生成证据：聊天对象、分组策略、消息数、记忆数、页面类型、Provider 和云端授权状态；即使生成被阻断，也应显示同一套证据，帮助用户判断下一步。
- 每条候选回复应显示风险等级和简短依据，但不直接展开完整聊天正文。
- 应能查看本次生成使用了哪些上下文和画像。
- 应能标记某条建议“好用”或“不合适”，用于后续优化。
- 回复反馈应作为本地结构化数据保存，只记录反馈值、候选短预览、风险、上下文 hash 和元数据，不保存完整 prompt 或 API Key。

### 6.5 可扩展性

- 平台适配器独立于核心 AI 和记忆系统。
- OCR 引擎可替换。
- LLM Provider 可替换。
- 分组策略可配置。
- 数据存储结构应支持迁移。

### 6.6 可测试性

- 支持保存匿名化调试样本。
- 支持用本地截图样本回放区域识别、页面分类、OCR 和消息解析。
- 支持为不同微信主题、窗口尺寸、DPI、多显示器坐标和平台 adapter 保存测试样本。
- 核心解析逻辑应与 UI 解耦，便于单元测试。
- 防抖、节流和任务取消逻辑应可测试。
- SQLite schema 迁移必须可验证，新增表或字段应覆盖从旧版本数据库升级、旧数据保留和迁移幂等。
- 数据库迁移清单必须在启动前校验版本唯一、连续、正整数且按顺序排列，避免发布包含重复或跳号迁移。

## 7. MVP 范围

### 7.1 必须实现

- PySide6 或 PyQt6 桌面应用。
- 主窗口。
- 跟随微信窗口的悬浮小部件。
- 检测微信窗口位置和可见状态。
- 支持微信窗口区域自动识别。
- 支持用户通过覆盖层手动校准聊天列表区、聊天记录区、标题区和输入区。
- 截取当前微信聊天区域。
- OCR 当前可见文本。
- 基础版面解析，区分自己和对方。
- 识别顶部会话标题。
- 基础页面类型分类，并在非聊天页暂停生成。
- 基础防抖、节流和截图内容去重。
- 手动选择或确认联系人分组。
- 根据分组策略生成 3 条回复建议。
- 点击回复建议复制到剪贴板。
- 本地保存联系人、分组和基础记忆。
- 主窗口显示日志、当前状态、当前聊天记录、当前聊天对象画像。
- 聊天对象列表和聊天对象详情页。

### 7.2 暂不实现

- 自动发送。
- 自动点击左侧聊天列表。
- 批量遍历联系人。
- 自动打开图片、语音、链接和小程序。
- 精准还原完整历史聊天记录。
- 多平台完整适配。

### 7.3 分阶段交付

Phase 0：技术探针

- 找到微信窗口并跟随悬浮窗。
- 截取微信窗口和右侧内容区。
- 验证 OCR 中文文本效果。
- 验证点击复制到剪贴板。

Phase 1：可用原型

- 主窗口和悬浮窗。
- 基础区域识别和手动校准。
- 当前会话 OCR。
- 生成并复制回复建议。
- 基础日志和当前状态面板。

Phase 2：记忆与画像

- 联系人确认、合并和分组。
- 本地 SQLite 存储。
- 当前聊天对象画像和聊天摘要。
- AI 提取记忆进入待确认状态。

Phase 3：稳定性增强

- 页面类型分类完善。
- 滚动防抖、截图 hash、AI 请求去重。
- 多显示器和 DPI 适配。
- 本地截图样本回放测试。

Phase 4：扩展能力

- 手动采集更多上下文。
- 更多聊天平台适配。
- 可选填入输入框但不发送。
- 本地模型离线模式。

## 8. 技术建议

### 8.1 客户端

- Python 3.11-3.13；启用 PaddleOCR 时首选 Python 3.12。
- PySide6 或 PyQt6
- pywin32
- mss 或 Windows Graphics Capture
- SQLite

### 8.2 OCR

候选：

- PaddleOCR
- RapidOCR
- Windows OCR

中文识别效果优先，速度和安装复杂度次之。

### 8.3 AI

支持多 Provider：

- OpenAI API
- OpenAI Compatible API
- 本地模型
- 其他兼容 OpenAI API 的服务

主页面设置中必须提供自定义 AI 配置：

- Provider 类型
- Base URL
- API Key
- Model
- Temperature
- Context token limit
- Timeout
- 连接测试
- 保存设置

连接测试要求：

- OpenAI-compatible Provider 必须发起真实轻量请求验证 Base URL、模型名、API Key 和返回结构。
- Local Preview 或 Disabled 模式不得发起网络请求。
- 测试日志只记录主机、路径、耗时、状态和错误摘要，不记录 API Key、完整 prompt 或聊天正文。

API Key 不应明文展示，不应写入日志。

首版可先抽象统一接口：

```python
class ReplyGenerator:
    def generate(context, profile, strategy, user_preferences):
        ...
```

### 8.4 存储

建议使用 SQLite。

核心表：

- contacts
- contact_aliases
- conversations
- messages
- memories
- strategies
- screenshots
- generation_logs
- reply_feedback

截图原图可选保存，默认可以只保存 OCR 结果和必要裁剪图，降低隐私风险和存储体积。

### 8.5 日志

日志应结构化，便于 UI 展示和问题定位。

建议字段：

```json
{
  "ts": "2026-08-03T11:00:00+08:00",
  "level": "info",
  "module": "ocr",
  "event": "ocr_finished",
  "conversation_id": "local_uuid",
  "snapshot_hash": "hash",
  "message": "OCR finished",
  "duration_ms": 312
}
```

日志不得记录 API Key。默认不记录完整聊天文本；调试模式下如需记录，应明确提示用户。

## 9. 风险与应对

### 9.1 OCR 误识别

应对：

- 保存 OCR 置信度。
- 低置信度上下文不写入长期记忆。
- UI 展示可疑内容。
- 允许用户修正。

### 9.2 联系人识别错误

应对：

- 不用昵称作为唯一主键。
- 支持手动确认和合并联系人。
- 当前联系人不确定时禁止写入长期记忆。

### 9.3 旧历史记录被当作最新上下文

应对：

- 记录 `observed_at` 和 `message_time`。
- 识别输入框、底部位置、回到底部提示等信号。
- 疑似历史页时标记 `history_snapshot`。
- 历史页不触发自动回复能力。

### 9.4 自动化误操作

应对：

- MVP 仅点击复制。
- 不实现自动发送。
- 不自动点击联系人列表。
- 所有高风险能力放入显式设置和白名单。

### 9.5 日夜间主题差异

应对：

- 主题检测。
- 颜色只作为辅助。
- 主要依赖几何布局、OCR 坐标、头像位置和控件区域。

### 9.6 Prompt 注入和模型误导

应对：

- 聊天内容不得覆盖系统策略。
- 联系人发来的“让 AI 忽略规则”等内容应作为普通消息处理。
- 模型输出必须经过结构化解析和基础安全检查。

### 9.7 性能和费用失控

应对：

- 截图 hash 去重。
- OCR 和 AI 请求限频。
- 任务队列只保留最新任务。
- 可配置每日 AI 请求上限。
- 主窗口展示请求次数和失败次数。
